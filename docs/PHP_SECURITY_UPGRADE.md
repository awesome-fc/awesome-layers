# PHP 公共层安全升级指引

更新日期：2026-10-22。

PHP 官方已披露 CVE-2026-109618（内存耗尽导致的内存破坏）和 CVE-2026-109619（请求之间的全局状态残留）。使用 PHP-FPM、CGI 等方式处理 Web 请求的业务，请优先核查当前使用的公共层，并升级到包含修复的版本。

## 版本选择

| 公共层 | 兼容运行时 / PHP 版本 | 不建议继续使用的版本 | 建议升级版本 |
| --- | --- | --- | --- |
| PHP81-Debian10 | `custom.debian10` / 8.1.28 | v1 | v2 |
| PHP80-Debian10 | `custom.debian10` / 8.0.29 | v2 及以前 | v3 |
| PHP81 | `custom` / 8.1.9 | v6 及以前 | v7 |
| PHP80 | `custom` / 8.0.22 | v7 及以前 | v8 |
| PHP72 | `custom` / 7.2.8 | 已发布的所有版本（含 v6） | 无修复版本，需迁移 |

以 PHP81-Debian10 v2 为例，官方公共层的 ARN 格式如下：

```text
acs:fc:{region}:official:layers/PHP81-Debian10/versions/2
```

使用时，将 `{region}` 替换为函数所在地域，并在控制台或查询结果中核对层信息。ARN 中的 `official` 标识、层名和版本号都应与所选公共层一致。公共层版本号是 ARN 末尾 `/versions/` 后的数字，与 PHP 版本号、测试账号中的层版本号以及构建产物的版本号不同。

上述 PHP 8.0/8.1 层将官方安全补丁回补到原有 PHP 版本，`php -v` 显示的版本号保持不变。因此，请通过公共层 ARN 和版本说明确认修复情况，不能仅凭 PHP 版本号判断。本次回补只针对上述两个漏洞，不改变 PHP 8.0/8.1 已结束官方支持的状态。系统和扩展的其他安全问题仍需单独评估。

## 兼容性变化

- **错误处理**：发生内存耗尽（OOM）或内存分配大小溢出时，PHP 会记录错误并立即退出，不再执行通过 `register_shutdown_function()` 注册的回调和对象析构函数。
- **会话上传进度**：该功能已在源码中关闭，无法通过 `php.ini` 重新开启。常规文件上传和会话功能仍需进行回归测试。
- **扩展版本**：部分扩展的版本可能与旧层不同，请验证应用所用扩展的兼容性。

## 升级步骤

1. 记录函数实际使用的运行时、完整公共层 ARN、函数版本及别名、启动命令和 PHP 可执行文件路径。检查 Composer 依赖要求、PHP 扩展，以及文件上传和会话相关配置。
2. 优先在同一系列公共层内升级。例如，PHP81-Debian10 从 v1 升级到 v2，保持 `custom.debian10` 运行时、`/opt/php8.1` 安装路径和已有环境变量。先在测试函数中绑定修复版本，再验证业务功能。
3. 通过实际使用的 HTTP、CGI 或 FPM 服务验证文件上传、会话、业务框架、数据库访问和错误处理，确认应用能适应上述兼容性变化。
4. 验证通过后，更新接收业务请求的函数配置、版本和别名。确认预留实例及其他旧实例已替换，旧函数版本不再接收请求。公共层发布新版本后，仍引用旧 ARN 的函数不会自动升级。

使用内置 `php7.2` 运行时的函数，不能仅通过挂载公共层或修改 PATH 替换平台提供的 PHP 解释器。迁移到自定义运行时需要调整启动脚本并验证业务。跨 PHP 版本或 Debian 发行版迁移时，还应检查语言特性、原生扩展的二进制兼容性（ABI）及动态库依赖，不能直接复制旧版 `.so` 文件。

## 长期迁移与临时缓解

PHP 7.2、8.0、8.1 均已结束 PHP 官方支持。补丁回补仅作为现有业务的过渡措施，长期建议迁移到仍受官方支持的 PHP 分支。各分支包含本次修复的最低版本分别为 PHP 8.2.35、8.3.36、8.4.27 和 8.5.12，迁移后仍需持续安装后续安全更新。PHP 8.2 的官方安全支持将在 2026 年底结束，不建议作为长期迁移的首选。选择新的 PHP 公共层前，请确认其兼容运行时和支持地域；也可以根据业务需要自行打包 PHP 或使用自定义容器。

暂时无法升级、且不依赖会话上传进度功能的业务，可以设置 `session.upload_progress.enabled=0`，并确认该配置已在实际处理请求的 PHP 进程中生效。此措施只能缓解会话上传进度相关的攻击，不能修复 OOM 漏洞。是否依赖该功能，需要结合代码、配置和实际请求确认，不能仅根据搜索结果判断。
